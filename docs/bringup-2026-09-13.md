No project implementation existed before this session. The supplied PDF is a
research reference, not an instruction file or an established implementation.

The attached printer is `Canon BJC-85`, USB `04a9:1055`, device release `0x0070`,
USB 1.1, serial `TEST-BJC85-0001`. Configuration 1, interface 0, alternate 0 is printer
class 7/subclass 1/protocol 2. Bulk OUT is `0x01`; bulk IN is `0x82`; both use
64-byte packets. Endpoint zero's maximum packet size is 8. Interface ownership
through ordinary user-space libusb succeeded.

The IEEE-1284 response was 93 bytes including its two-byte big-endian length:

```text
MFG:Canon;CMD:LQ,BJL,BJRaster,BSCC;MDL:BJC-85;CLS:PRINTER;DES:Canon BJC-85;VER:1.10;STA:10;
```

Printer class status was `0x18`: selected, no error reported, paper not reported
empty. This is not evidence of ink availability or installed cartridge type.
`STA:10` remains uninterpreted. Cartridge type in this initial baseline was
operator-reported BC-11e; the subsequent IS-12 experiment is described below.

supports investigating ink delivery; it does not prove that every raster field

## Independent hardware control

Canon's BJC-85 user manual describes a built-in nozzle check: load plain paper,
turn the printer off, hold POWER until four beeps, then release. The printer
generates its own pattern. The user performed this check and supplied a photograph
showing cyan, magenta, and yellow ladders with no visible black. This establishes
a black ink-delivery problem independently of this project's raster pipeline.
It does not establish whether the black tank is empty/dried or its nozzles are
clogged or failed. The photo is preserved unchanged as
`artifacts/original/onboard-nozzle-check-2026-09-13.jpg`, with its hash in the
provenance manifest. Procedure source: [Canon manual, printed page 55](https://www.manualowl.com/m/Canon/BJC-85/Manual/38512?page=55).

The native colour fixture now uses saturated blue text, a blue one-inch square,
blue fine lines, and labelled cyan/magenta/yellow/black patches. This allows
visible print-path validation with the working colour inks; the black patch is
a control and may remain blank. This source-artwork change does not alter PDF
rendering or the monochrome fixture.

After the user confirmed that multiple sheets were loaded, the colour fixture
was submitted once. The revised sender accepted all 209,181 bytes and returned
success without a manual resume. Its record is
[`color-print-transfer.txt`](protocol/color-print-transfer.txt). The user supplied
a photograph of the result with a ruler: upright readable text, cyan/magenta/
yellow patches, visible fine lines, and a blank black control patch. There are
no obvious missing large bands in the photo. The ruler is consistent with a
one-inch horizontal square edge; camera perspective and the obscured top edge
prevent a precise two-axis measurement. This is the first confirmed visible
native ARM64 print from the project.

The unchanged photo is `artifacts/original/native-color-print-2026-09-13.jpg`,
SHA-256 `947d447a26fb586cc78ffbf23c8c74c86a9a51d1d6e1f7299135da4284e77e35`.

BC-11e is the cartridge/printhead assembly; BCI-11 Black and BCI-11 Color are its
ink tanks. Buying tanks alone may not repair a dried or failed printhead.
Do not call a replacement purchase sufficient until the internal pattern and
hardware condition are understood. Reference: [Canon BJC-80 manual, same BC-11e assembly](https://gdlp01.c-wss.com/gds/0/0900007420/01/BJC80_user_manual.pdf).

## Native macOS queue

The `BJC85_Native` queue, displayed as **Canon BJC-85 Native**, uses macOS's
built-in IPP Everywhere support. CUPS produces Apple Raster (`image/urf`), which
the native PAPPL 1.4.12 adapter reads, crops to Gutenprint's imageable area, and
encodes for the exact `bjc-85` model. The adapter spools the complete raw document
before sending USB data. No legacy Canon executable or emulation is in this path.

One colour page was submitted as CUPS job `BJC85_Native-3`. Its generated stream
was 220,040 bytes, SHA-256
`a221c5c5538ff169e879a9a8395f22849021084e87939734a80a72c5c75c748b`.
All bytes were accepted without a manual resume; CUPS reported completion at
20:01:48 UTC. Asked whether this second page was upright and readable with the
same CMY patches, the user replied **"Yes, it looks correct"**. This verifies
the ordinary macOS queue path in addition to the earlier direct-USB print.
See [`ipp-hardware-print.json`](protocol/ipp-hardware-print.json).

The service advertises Letter/A4, 360 dpi, colour/grayscale, single-sided
printing, and copies. Six IPP acceptance checks passed in an ASAN/UBSAN build:
valid capability attributes, Letter colour raster, four-page A4 grayscale with
two copies, accounting for eight impressions, and rejection of unsupported
180 dpi and Legal paper. These raster tests used `--dry-run` and sent no USB
data. They establish software behaviour, not physical A4/multipage acceptance.
All three CTest tests also passed under sanitizers. The upstream static libraries
were not instrumented.

Two restart checks verified retention of completed job history and continuation
of job IDs. A synthetic recovery marker caused the next dry-run job to abort
before rendering or USB output, with zero impressions. Records:
[`ipp-acceptance.txt`](protocol/ipp-acceptance.txt),
[`ipp-restart.txt`](protocol/ipp-restart.txt), and
[`ipp-recovery.txt`](protocol/ipp-recovery.txt).

The web-page smoke test exposed a PAPPL 1.4.12 null footer passed into localization.
A crash report and an isolated sanitizer reproduction identified this call path.
Setting a footer through the public API fixed it; the home, printing-defaults,
and jobs pages then returned normally, with IPP still responsive. A separate
early integration crash came from PAPPL's limited log formatter handling `%zu`;
the adapter now formats messages with `vsnprintf` and passes a single `%s`.
No upstream source modifications were needed.

The final native build is installed as the current user's login service
`local.bjc85.native-print`. Its LaunchAgent is under `~/Library/LaunchAgents/`;
private state/spool/logs are under `.state/` in this project. At installation,
launchd reported it running, IPP reported idle/accepting jobs, and the listener was solely
`127.0.0.1:8631`. The installed attributes passed validation:
[`ipp-installed-attributes.txt`](protocol/ipp-installed-attributes.txt).
The temporary `BJC85_Native_Test` queue and dry-run service were removed/stopped.
The pre-existing `_0_0_0_0` and `PDFwriter` queues and default destination remain.

This remains a local development installation. It retains raw job files,
requires the current project/Homebrew paths, and has no automatic cartridge
detection. Stop the service before swapping in IS-12 or using the direct sender.
Cancellation is checked during rasterization and between USB transfers; a
journal created before output prevents automatic replay after a crash or a
known partial transfer. Physical cancellation, unplug/replug, sleep/wake and
long-run reliability have not passed hardware acceptance.

## Scanner status

Original Mac and Windows packages were acquired, hashed, and statically unpacked.
The Windows package explicitly lists BJC-85 support. See
[IS-12 analysis](protocol/is12-analysis.md).

After the successful queue print, the user installed the IS-12. At 20:19:25 UTC
the CUPS queue was disabled with a scanner-specific reason and the print service
was booted out of launchd. Both remain paused/stopped for scanner testing. The
LaunchAgent plist remains installed; restore BC-11e before restarting the
service and enabling the queue. Automatic print-path cartridge detection is
still unimplemented.

The read-only USB baseline with IS-12 returned the same descriptors, IEEE-1284
identity (including `STA:10`) and class status as BC-11e. Native ARM64
`bjc85-is12` then sent the scanner-mode entry and three information queries
reconstructed from Canon's driver. Every request was fully accepted and every
expected reply arrived with the predicted framing. Carrier `b0 … 0e` and
information `70 …` pass the model-specific IS-12 head checks. This establishes
native bidirectional scanner communication and positive head identification.

The first status was `00 08 00`. The driver trace links bit 0x08 in the second
byte to the `PREHEAT` dialog, whose resource says "Warming up scanner cartridge."
A later query and asynchronous update both returned `00 00 00`, showing that
warm-up cleared. Two additional queries returned a one-byte raw temperature
and 18-byte extended-information block. No temperature unit is asserted.

Records: [wire reconstruction](protocol/is12-wire.md),
[first status](protocol/is12-first-status.jsonl),
[warm-up completion](protocol/is12-status-after-warmup.jsonl),
[extended information](protocol/is12-extended-status.jsonl), and
[streaming-parser hardware check](protocol/is12-stream-status.jsonl).
The final diagnostic completes in about 0.8 seconds and handles successful
zero-length USB IN packets without waiting out each five-second deadline.

Five CTest checks pass under ASAN/UBSAN. The scanner tests replay three real
captures at different byte/chunk boundaries and exercise a synthetic 12,337-byte
calibration record across outer frames, plus incomplete/malformed streams.
This validates parsing; it is not a calibration or scan result.

The user has neither the white calibration sheet nor a scanning holder. The
two printed test charts are available as future image targets. Canon's manual
requires white calibration for first use and a holder for image feeding; an ordinary
sheet has not been demonstrated to be an adequate replacement. Protocol analysis
can continue without them, but calibrated scan acceptance cannot yet pass. No
feed, calibration, or image-acquisition command has been sent.

## Native image acquisition and white-paper correction

Subsequent work superseded the earlier status-only limitation. The user requested
scanning the loaded printed charts, and both were acquired at 90 dpi through
native USB. Raw colour data initially showed a dark cast and horizontal shading.
A clean white sheet supplied a complete 12,337-byte reference measurement.
Static Ghidra analysis reconstructed the mode selection, fixed-point field and
temperature corrections, per-channel scaling, and T download. The resulting
90 and 180 dpi chart scans have readable text and a white background.

The native C decoder plus ImageIO matches an independent Python decoder exactly
for both original charts and the corrected 90/180 dpi captures. Both decoded
orientations and raw journals remain available. The native AppKit application
now connects, calibrates, scans, previews, rotates, cancels, and saves images;
PDF export passed its first UI acceptance and preserves an 8 × 10.8 inch page.

The earlier absence of Canon's accessories did not prevent these controlled
plain-paper experiments. The results do not establish factory colour accuracy
or qualification of other media. See [acquisition evidence](protocol/is12-acquisition.md)
and [calibration arithmetic](protocol/is12-calibration-trace.md). The older
`is12-native-milestone.json` remains a historical status-only snapshot;
`is12-native-scan-manifest.json` records the later result.
